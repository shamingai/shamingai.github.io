用 SDD 模式搭建一个 Gitee 博客

规格驱动开发（Spec-Driven Development，SDD）把「要做什么」写成可持续使用的规格，再让实现跟着规格走。GitHub Spec Kit 对它的定义是：规格不再是写完就丢的脚手架，而是后续规划、任务和实现的上下文。官方核心顺序是 Specify、Plan、Tasks、Implement，再以 Converge 检查实现是否真的完成。需要把决定问清楚时，在 Plan 之前加入 Clarify。资料见 [Spec Kit 文档](https://github.github.com/spec-kit/)、[什么是 SDD](https://github.github.com/spec-kit/concepts/sdd.html) 和 [快速开始](https://github.github.com/spec-kit/quickstart.html)。

先定边界，再选技术

SDD 要求规格写用户能观察到的行为和原因，不在这一阶段决定语言和框架。技术选择留到 Plan。这次会话遵守了这个顺序。

最初的描述只是「做一个 Gitee 博客，前后端分离，使用 Git 上传下载」。规格没有写 Java、Vue 或 MySQL。Clarify 连续问了四个会改变产品形态的问题，答案都写回 `specs/001-gitee-blog/spec.md`：

- 仓库在作者自己的 Gitee 上。网站只读取和展示，不接收 Git 推送。

- 全站只有一位作者、一个当前绑定的仓库。文章在本地写完，再用 Git 上传。

- 只有约定目录中的文章文件算博客，其余文件忽略。

- 具体约定是 `posts/` 目录中的 `.md` 文件。第一行是标题，其余内容是正文。

这些问题不是文案偏好。它们决定网站要不要实现 Git 服务、有没有多作者、测试样本该放哪个文件。没有这些答案就进入实现，后面几乎一定返工。

原则先于功能

项目开始时先写了宪法：代码质量优先、测试覆盖率不低于 80%、接口遵循 REST、前后端分离。Spec Kit 的快速开始也建议每个项目先建立 constitution，再进入功能规格。

这四条后来都变成了可检查的约束。Plan 选择了 Java 21、Spring Boot、Vue 3 和原生 JavaScript，是因为用户在规划阶段明确提出；MySQL 也是在那时指定的。契约放在 `contracts/http-api.md`，没有使用带动词的路径。重新读取仓库是创建一个资源，而不是在查询博客时顺带触发。

从规格到可执行任务

Plan 之后，Tasks 按用户故事拆成 39 项，而不是按技术层堆成一张长清单。三个故事可以分别验收：

1. 绑定自己的 Gitee 仓库，并只导入合法文章。

2. 主动重新读取，让网站反映新增、修改和删除；读取失败时保留上次成功的内容。

3. 未登录访客阅读列表和正文。

Implement 按这个顺序落地。后端测试覆盖了绑定、读取、分页和失败路径，行覆盖率达到 84.2%。前端用 Vue 3 和原生 JavaScript 提供阅读、绑定和重新读取页面。

这次没有按理想路径走完的地方

SDD 不能掩盖环境事实。规划写的是 MySQL 8.4，但本机 MySQL 拒绝了当前用户登录，也没有可用的 Docker。为了让服务能够启动，本地运行改用了 H2 文件库。这是一次偏离，应记录为部署前要补上的验证，而不是假装已经在 MySQL 上验收。

另外，官方完整路径还有 Checklist、Analyze 和 Converge。这次会话执行了 Constitution、Specify、Clarify、Plan、Tasks 和 Implement，没有跑完后面的一致性检查。所以「代码已经写完」不等于「规格、规划和实现已经收敛」。

服务启动也遇到了工具超时：第一次前后端进程被超时停掉，随后用不受该超时限制的方式重新启动。读者看到的空列表是正确状态，因为还没有绑定仓库，不是读取失败。

可以复用的做法

用 SDD 搭建这个博客，真正起作用的不是多写了几份 Markdown，而是每个阶段只回答自己的问题。Specify 回答读者和作者能做什么。Clarify 把会改变数据模型和验收方式的决定问完。Plan 才引入 Java、Vue 和数据库。Tasks 让每个故事都能单独验证。Implement 必须用测试和覆盖率证明规格里的行为存在。

如果需求变了，应该先改规格中的对应句子，再决定规划和任务是否作废。这次会话中曾经删除两套旧规格并重新 Specify，就是因为产品模型已经从「站内发布博客」变成了「展示外部 Gitee 仓库」。保留旧规格会让后续命令对着错误的事实继续工作。
