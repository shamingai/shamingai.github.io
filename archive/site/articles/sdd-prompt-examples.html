这些实例来自这次搭建 Gitee 博客的会话。它们按 Spec Kit 的阶段分开：每一条提示词只要求当前阶段回答的问题，不把后面的技术决定提前塞进去。

先定项目原则

`/speckit.constitution 制定项目原则：代码质量优先、测试覆盖率>80%、API 设计遵循 RESTful 规范、前后端分离`

这一步只写长期约束。它没有提到博客功能，也没有指定 Java 或 Vue。后面的规划必须对照这些原则，而不是临时解释为什么可以不测试。

描述要做什么

`/speckit.specify 需要开发一个gitee博客，前后端分离，使用git上传下载`

这里只写用户能观察到的结果：内容用 Git 上传和下载，阅读与写作路径分开。没有写数据库、框架和接口路径。Spec Kit 的 Specify 阶段负责 what 和 why；技术栈留到 Plan。

如果需求模型变了，不要在旧规格上补一句。这次先删除旧的 001 和 002，再用上面的提示词重新 Specify，避免后续命令继续读取过时事实。

把关键决定问清楚

`/speckit.clarify`

这条提示词不需要附带长说明。Clarify 会一次问一个会影响架构、数据或验收的问题。这次实际回答了四个：

- 仓库由作者自己的 Gitee 提供，网站不接收推送。

- 网站只展示一位作者。

- 只认约定目录中的文章文件。

- 约定目录是 `posts/`，文章是 `.md`，第一行是标题。

回答要短且明确，例如 `A` 或一句不超过范围的话。不要在回答里顺便指定框架，那会把 Plan 的决定提前混入规格。

到规划阶段再给技术栈

`/speckit.plan 使用原生 JavaScript 和 vue.js 构建前端UI，java构建后端程序，数据存储在 mysql 中`

这是技术提示词应有的位置。它给出语言、前端框架、后端语言和存储，但不重新描述博客功能。规划阶段会把它写成技术上下文、数据模型、接口契约和验证步骤。

如果只是想记录提示词，而不是改变已有技术方案，可以说：

`/speckit.plan md 的格式写即可，写一下提示词实例`

这条提示词把输出格式限定为 Markdown，并把内容限定为实例，避免覆盖已经通过的 `plan.md`。

拆任务和实现

`/speckit.tasks`

不附加技术要求。任务阶段应从规格和规划中拆出可独立验收的用户故事，而不是重新选择框架。

`/speckit.implement`

实现阶段也不追加新的产品需求。它应按 `tasks.md` 执行，并用测试和覆盖率证明结果。临时遇到的环境问题应单独说明，不要写回规格假装已经满足。

写文章也用阶段边界

`/speckit.clarify 搜索网络涉及SDD相关内容，和本次会话，写一篇 SDD 模式搭建博客的文章`

这条提示词同时要求外部资料和本次会话证据。文章应区分官方流程与实际执行结果，不能把没有运行的检查写成已完成。

`/speckit.clarify md格式，用001的博客展示`

这是展示要求，不是新的产品澄清。它要求 Markdown 原文和 001 博客页面都能看到文章，但不要求修改博客规格。

使用这些提示词的规则

- Specify 不写框架、数据库和接口。

- Clarify 只回答当前问题，不提前选择技术。

- Plan 才写 Java、Vue、MySQL 或输出格式。

- Tasks 和 Implement 不增加新功能。

- 每次提示词只做一件事。需要文章、展示和规划变更时，分成三次请求。
