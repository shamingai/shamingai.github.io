# Feature Specification: 每日热门前十资讯博客

**Feature Branch**: `003-daily-top10-news`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "/speckit.specify 我要做一个每天生成前十资讯的博客的功能：核心功能：1、搜索各大网站，查看点击量最高的页面；2、整理这些资讯内容、推荐理由和跳转链接；3、把整理完成的内容，每天生成一篇博客，标签是资讯类的。"

## Clarifications

### Session 2026-10-17

- Q: 「各大网站」具体指哪些站点？ → A: 由作者维护的站点清单，首批为中国大陆可访问的综合门户、科技媒体和社区热点榜。
- Q: 点击量排名如何获取？ → A: 优先读取站点公开的热榜、排行、热门文章页面；没有公开排行的站点按其在这些页面上的排位记录来源排名。不爬取站点后台统计，也不把缺少排行的站点排除。
- Q: 「整理内容」由谁完成？ → A: 由作者本地的语言模型按提示词生成，系统只负责收集、去重、校验和落盘；不调用任何付费资讯 API。
- Q: 「每天」如何触发？ → A: 作者电脑上每天定时执行一次，结果随 Git 推送到仓库；网站只读取，不在服务器端抓取或生成。
- Q: 资讯博客是否进入现有博客的列表、归档、分类和搜索？ → A: 是。它与作者手写文章共用同一条展示链路，并带「资讯」标签。

### Session 2026-10-18

- Q: 网站和资讯生成本身采用什么部署形态？ → A: 前后端分离，后端单独部署。后端是独立进程、自带数据存储、对外只提供 HTTP/JSON 接口；前端单独构建并单独部署，只通过该接口读取数据。每日资讯采集与整理在独立的后端服务中完成，不在静态站点生成器里做。
- Q: 读者站点是否改为读取后端接口？ → A: 是。列表、正文、归档、分类、标签、搜索、关于、历史和全部每日资讯都经后端接口提供，前端不再依赖预生成的静态数据文件。
- Q: 后端不可用时读者看到什么？ → A: 每个页面显示明确的加载失败提示和重试入口，不显示空列表冒充「没有文章」。
- Q: 每日资讯的生成由什么触发？ → A: 由作者本地保留的定时调度器每天（上海时间 08:00）调用受鉴权的后端管理接口来触发；后端自身的定时调度器不承担生产触发。采集、整理仍全部在后端服务内完成；作者也可以随时手动触发或要求重生成。
- Q: 生成成功后，当天的资讯博客如何到达线上站点？ → A: 后端把当天的博客写入站点内容目录（`blog/content/posts/daily-YYYY-MM-DD.md`）并记录到后端数据库；前端经接口读取。后端不自动 commit/push，推送由作者手动完成。
- Q: 当天去重、校验后入选条目不足十条时，系统应该怎么做？ → A: 仍生成博客，按实际数量收录，并在开头说明不足十条及主要原因；接口返回成功，不以不足十条作为失败。只有当站点均无可用内容、一条都收集不到时才不生成并报错。
- Q: 每日资讯博客的正文在网站上如何渲染？ → A: 作为普通文章走统一的正文阅读链路（列表、正文、归档、标签、搜索共用同一套字段与渲染），`GET /api/digests/{date}` 的结构化 `items` 只作为附属于该文章的增强数据，不单独承担正文渲染。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每天得到一篇当天的前十资讯博客 (Priority: P1)

作者本地保留的定时调度器每天（上海时间 08:00）调用后端的管理接口触发一次生成。后端从清单中的各大站点收集热点页面，按热度排出前十，为每条资讯写出标题、摘要、推荐理由和原文链接，生成一篇当天的博客并保存到站点内容目录，标签带「资讯」。

**Why this priority**: 这是整个功能的存在理由。没有它，后面的阅读、跳转和展示都没有内容。

**Independent Test**: 在固定测试数据下通过管理接口触发一次生成，确认产生一篇日期为当天、恰好十个条目的博客，每条都有标题、摘要、推荐理由和跳转链接，且带「资讯」标签。

**Acceptance Scenarios**:

1. **Given** 今日尚未生成资讯博客，站点清单中有可用站点，**When** 定时调度器调用生成接口，**Then** 产生一篇当天的资讯博客，包含十条目，每条显示标题、摘要、推荐理由和可跳转的原文链接。
2. **Given** 某条资讯来自排行页面，**When** 作者查看该条，**Then** 能看出它来自哪个站点、在该站点的排名，以及被推荐的理由。
3. **Given** 今日的资讯博客已生成，**When** 同一天再次请求生成且未要求重生成，**Then** 默认不产生第二篇当天的博客，并明确提示今天已生成。
4. **Given** 生成成功，**When** 读者刷新站点，**Then** 资讯博客与手写文章一样出现在列表和正文阅读中；线上静态构建的同步由作者按自己的节奏推送仓库完成，不影响接口读者立即可读。

---

### User Story 2 - 条目可追溯、可复核 (Priority: P2)

作者生成后快速浏览这篇博客，能确认每条资讯都有真实可打开的原文链接、来源站点和推荐理由；不合格的条目会被替换或在博客中明确标出。

**Why this priority**: 自动整理的内容最容易出现编造链接、张冠李戴和重复条目。读者点击跳转后发现内容对不上，会直接破坏博客的可信度。

**Independent Test**: 构造一条没有可用链接、一条与另一条重复、一条只有标题没有正文的候选资讯，确认最终博客中每条都有可打开的链接且没有重复，被剔除的情况在生成结果中可见。

**Acceptance Scenarios**:

1. **Given** 一条候选资讯的链接无法打开或缺失，**When** 生成完成，**Then** 该条不被收录，并被后续次高排位的候选补位。
2. **Given** 两条候选指向同一篇原文，**When** 生成完成，**Then** 博客中只出现一次。
3. **Given** 摘要或推荐理由无法基于原文可靠写出，**When** 生成完成，**Then** 该条被剔除而不是留下空泛内容；可收录条目不足十条时，博客收录实际数量并说明原因。
4. **Given** 生成完成，**When** 作者核对某一条，**Then** 能根据博客中记录的来源站和排名回到原始排行位置。

---

### User Story 3 - 在网站上阅读当天的资讯 (Priority: P3)

读者在博客站首页看到当天的资讯博客，进入后以与手写文章相同的方式阅读正文，按排名看到十条摘要，并点击任意一条跳转到原文。

**Why this priority**: 内容已经生成后，读者能顺畅阅读并跳转才让这个功能对读者产生价值；它依赖现有博客展示能力，因此排在生成之后。

**Independent Test**: 准备一篇资讯博客，打开首页和正文页，确认出现在列表中、带「资讯」标签、十条按排名显示、链接指向原文。

**Acceptance Scenarios**:

1. **Given** 今天已有一篇资讯博客，**When** 读者打开首页，**Then** 这篇博客出现在最新文章中，并显示「资讯」标签。
2. **Given** 读者打开一篇资讯博客，**When** 阅读内容，**Then** 看到日期和十条按排名排列的条目，每条有标题、摘要、推荐理由和原文链接；正文的加载、失败提示与重试行为与手写文章完全相同。
3. **Given** 读者选择「资讯」标签，**When** 查看标签页，**Then** 看到所有日期的资讯博客按日期从新到旧排列。
4. **Given** 读者搜索某条资讯的标题中的关键词，**When** 搜索，**Then** 当天的资讯博客出现在结果中。

---

### User Story 4 - 调整生成规则与站点清单 (Priority: P4)

作者可以增删站点、调整每个站点保留的候选数量，或临时跳过某天。

**Why this priority**: 站点可访问性和热点来源会变化，没有调整能力的功能很快会失效；它不影响第一次跑通，所以优先级最低。

**Independent Test**: 从清单中移除一个站点并加入一个测试站点，执行生成，确认结果只来自新清单。

**Acceptance Scenarios**:

1. **Given** 作者移除一个站点，**When** 执行生成，**Then** 结果不包含该站点的资讯。
2. **Given** 清单中一个站点当天不可访问，**When** 执行生成，**Then** 其余站点继续，生成结果中记录该站点本次失败。
3. **Given** 清单中的站点当天都没有可用内容，**When** 执行生成，**Then** 不生成空博客，并明确提示失败原因。

---

### Edge Cases

- 同一天重复执行：默认保留已有的当天博客，不覆盖、不追加；只有作者明确要求重生成时才替换。
- 跨天执行：以上海时间（UTC+8）的日期为准决定「当天」。
- 不足十条：收录实际数量，并在博客开头说明本次不足十条及主要原因。
- 一条都收集不到：不生成博客，返回失败结果并说明各站点失败原因。
- 原文在生成后被删除：博客本身不失效，读者点击时由原文站点给出提示。
- 内容语言：原文为中文时摘要和推荐理由使用中文；原文为英文时保留英文原题并提供中文摘要。
- 重复资讯：同一原文或标题高度相似的条目只保留热度更高、来源更权威的一条。
- 站点改版导致排行页结构变化：该站点本次记为失败，不影响其他站点和已生成的博客。
- 单条摘要过长：博客中每条摘要和推荐理由都限制在便于扫读的长度内，超出时截断并保留原文链接。

## Requirements *(mandatory)*

### Functional Requirements

**收集**

- **FR-001**: 系统 MUST 从作者维护的站点清单收集当日热点候选，清单中每个站点 MUST 记录显示名称、站点地址和热榜入口，并 MUST 支持随时增删。
- **FR-002**: 对每个站点，系统 MUST 优先读取其公开的热榜、排行或热门文章页面，并 MUST 记录每条候选在该站点的排位。
- **FR-003**: 系统 MUST 记录每条候选的来源站点、原文链接、原题、发布时间（如可得）和被采集的次数（同一原文被多个站点提到视为更热）。
- **FR-004**: 系统 MUST 为每次生成记录每个站点的采集结果（成功、失败及原因），并 MUST 在失败时继续处理其余站点。
- **FR-005**: 系统 MUST NOT 绕过站点的访问限制、登录或付费墙；受限内容 MUST NOT 被收录。

**整理**

- **FR-006**: 系统 MUST 对候选去重，同一原文只保留一条。
- **FR-007**: 系统 MUST 为每条入选资讯生成不超过 200 字的摘要、不超过 100 字的推荐理由，并 MUST 保留可跳转的原文链接。
- **FR-008**: 摘要和推荐理由 MUST 基于原文内容生成；无法可靠生成时该条 MUST 被剔除，而不是留下空泛或编造的内容。
- **FR-009**: 系统 MUST 按热度选出前十名并将排名固定写进博客；收录条目不足十条时 MUST 按实际数量收录，并在博客开头说明原因；只有一条候选都收集不到时才 MUST 不生成博客并返回失败结果。
- **FR-010**: 系统 MUST 校验每条入选资讯的原文链接可访问；不可访问的条目 MUST 被剔除并由下一名次补位。

**生成与发布**

- **FR-011**: 系统 MUST 在每次生成时产生一篇博客，日期为上海时间当天，标题 MUST 含当日日期，标签 MUST 含「资讯」，并 MUST 保证同一日期最多一篇。
- **FR-012**: 每篇资讯博客 MUST 按排名展示入选条目，每条包含排名、标题、来源站点、摘要、推荐理由和原文链接。
- **FR-013**: 同一日期再次生成时，系统 MUST 默认保留已有博客；覆盖 MUST 仅在作者明确要求时发生。
- **FR-014**: 资讯博客 MUST 作为普通文章进入现有博客的列表、正文阅读、归档、标签和搜索，与其他文章使用同一套展示字段与正文渲染；结构化的条目数据 MUST 只作为该文章的附加数据，不另建一套详情页渲染。
- **FR-015**: 系统 MUST 提供一次执行的汇总结果，说明收录条数、每站成功与失败情况、被剔除条目的原因。
- **FR-016**: 后端 MUST 把当天生成的博客写入站点内容目录，并 MUST 同时记录在自身数据存储中，供读接口返回；后端 MUST NOT 自动提交或推送站点仓库。
- **FR-017**: 后端 MUST 提供受鉴权的管理入口用于触发当天生成与重生成；后端自身的定时调度器 MUST NOT 作为生产环境的触发来源，每日触发由作者本地的定时调度器调用该入口完成。

### Key Entities

- **来源站点 (Source Site)**: 作者维护的一个资讯来源，含显示名称、地址、热榜入口和启用状态。
- **候选资讯 (Candidate)**: 一次采集得到的一条热点，含来源站点、原文链接、原题、站内排名、发布时间、被提及次数。
- **入选资讯 (Picked Item)**: 经过去重、内容生成与链接校验后进入前十的条目，含最终排名、摘要、推荐理由。
- **每日资讯博客 (Daily Digest)**: 某日期的一篇博客，含日期、条目列表、采集汇总说明。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在站点均可访问的正常情况下，一次生成能得到十条目完整的当天资讯博客，且不需要人工修改即可发布。
- **SC-002**: 生成的博客中链接不可访问、链接与标题不匹配的条目数为 0。
- **SC-003**: 同一日期生成的资讯博客数不超过 1 篇。
- **SC-004**: 生成成功后的下一次请求即可在「资讯」标签页看到新博客；站点仓库中的 Markdown 文件在作者下一次推送后与接口内容一致。
- **SC-005**: 单个站点失败时，其余站点仍能完成生成；一次生成中因站点结构变化导致的整体失败次数为 0。
- **SC-006**: 作者从触发生成到审阅完成不超过 10 分钟。
- **SC-007**: 触发一次生成后，作者无需在服务器上做任何人工步骤即可在下一次请求中读到当天的博客；后端定时调度器关闭也不影响每日生成。

## Assumptions

- 「各大网站」由作者维护的站点清单决定，首批以中国大陆可访问的站点为主；清单内容留到规划阶段确定。
- 站点公开的热榜/排行为热度来源；能获得点击量的站点记录其点击量，不能获得的以站内排名记录热度，不追求跨站点统一口径。
- 摘要是对原文核心信息的重述，不整段转载原文。
- 生成在后端服务内执行，由作者本地的定时调度器每天调用管理接口触发；网站端只读取生成结果，不抓取外部站点。
- 语言模型由后端服务调用，作者本地只需保留触发用的调度器和访问令牌；不新增任何外部付费资讯服务。
- 「资讯」标签名称与现有标签体系不冲突；如已有同类标签，规划阶段合并为同一标签。
- 每日并发站点数量与重试策略留到规划阶段确定；每日生成时间已定为上海时间 08:00，由作者本地调度器触发。
