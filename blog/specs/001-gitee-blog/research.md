# Research: Gitee 博客

## 1. 发布形态

- Decision: 本地写作，生成静态站点后发布。站点不提供在线编辑、后台、仓库绑定或同步入口。
- Rationale: 规格已确认文章在本地写成，网站只展示已发布内容。继续使用运行中的后端读取 Gitee 会重新引入后台和上传边界。
- Alternatives considered: 保留 Spring Boot 同步服务。它能读仓库，但提供作者操作和运行时内容管理，违反 FR-002。

## 2. 读者站点与生成器的边界

- Decision: 读者看到的是生成后的静态页面。排序、字数、阅读时间、目录、分类数量和相邻文章在生成时计算，并写入页面。
- Rationale: 静态站点发布后没有服务器可再计算这些结果。生成时计算一次，读者每次打开得到同一结果，满足顺序稳定的要求。
- Alternatives considered: 浏览器打开后再计算。刷新时机和脚本失败会让顺序、数量和相邻文章不一致。

## 3. 写作输入

- Decision: 作者在本地以文章、关于和历史三类内容作为生成输入。文章必须有标题、发布日期和恰好一个分类；摘要和标签可缺省。具体文件格式留在实现任务中选择，计划不把格式写成读者需求。
- Rationale: 规格明确不定义写作文件格式，但生成器必须知道哪些字段决定能否发布。
- Alternatives considered: 在计划中固定某一种标记格式。那会把实现选择提前写成读者契约。

## 4. 发布资格

- Decision: 正文为空、分类缺失、分类多于一个或发布日期无法识别的文章不进入站点。生成器必须报告文件身份和原因。合法文章继续发布。
- Rationale: 规格要求未发布文章不出现在任何读者入口，也要求多个分类的文章不被发布且能被作者定位。
- Alternatives considered: 自动选择第一个分类。这会隐藏作者错误，并可能把文章放到错误分类。

## 5. 排序

- Decision: 首页、分类、标签和搜索按发布日期从新到旧；归档年份内从旧到新。日期相同都按读者可见标题排序。上一篇和下一篇只跟随首页顺序。
- Rationale: 澄清结果已经分开规定这些顺序。生成时固定排序，避免页面各自实现一套比较规则。
- Alternatives considered: 全站只用一种顺序。归档已明确要求从旧到新，不能并入首页顺序。

## 6. 分类数量

- Decision: 分类数量只统计直接归入该分类的已发布文章。父分类不列出、不累计子分类文章。
- Rationale: 澄清确认父分类与子分类的文章互不继承。
- Alternatives considered: 父分类显示包含子分类的总数。这会让同一篇文章被两级数量重复计算，验收无法判断。

## 7. 搜索

- Decision: 生成一份只含已发布文章标题、摘要和正文的搜索数据。页面用关键词在这份数据中查找，结果使用首页顺序。空关键词不搜索。
- Rationale: 规格要求全站入口、只查已发布文章，并在 1 秒内返回。45 篇规模不需要单独搜索服务。
- Alternatives considered: 服务端搜索。它需要运行中的后端，超出静态发布边界。

## 8. 关于与历史

- Decision: 关于和历史是独立生成页面。历史事件可记录文章入口，但入口只在该文章已发布时保留。历史事件不进入归档、分类、标签或搜索。
- Rationale: 规格要求三者互不替代，并要求失效文章入口被移除而事件保留。
- Alternatives considered: 从文章发布日期自动生成历史。这会把历史变成另一种归档。

## 9. 现有代码的处理

- Decision: 现有 `backend/` 与绑定、同步页面属于旧规格。新实现不扩展这些入口。替换范围由 `/speckit-tasks` 决定，本计划只禁止把新阅读能力加到旧后台流程上。
- Rationale: 宪法要求前后端分离，但不要求保留一个已经与新规格冲突的运行时后端。
- Alternatives considered: 在现有 API 上补充分类和搜索。这会继续提供后台式内容管理，不能通过规格验收。
